1. PRESENTATION GENERALE DU PROJET

Le projet s'appelle WACDO.

WACDO est une application web de commande inspirée d'une borne de restauration rapide.

Le projet contient trois grandes parties :

1. Une borne client :
   - elle permet de consulter un catalogue ;
   - elle permet de choisir des produits ou des menus ;
   - elle permet de constituer un panier ;
   - elle permet d'envoyer une commande au backend.

2. Une API backend :
   - elle fournit le catalogue ;
   - elle reçoit les commandes ;
   - elle calcule les prix ;
   - elle vérifie les disponibilités ;
   - elle met à jour les stocks ;
   - elle protège les routes sensibles.

3. Un back-office :
   - il permet aux employés, managers ou administrateurs de se connecter ;
   - il permet de consulter les commandes ;
   - il permet de voir le détail d'une commande ;
   - il permet de changer les statuts ;
   - il permet de consulter et modifier certains produits, menus et ingrédients.

Objectif du projet :
Permettre à un client de passer une commande simplement depuis une borne, tout en donnant au restaurant un outil de suivi et de gestion côté back-office.

4. JUSTIFICATION DES CHOIX TECHNIQUES

Pourquoi PHP ?

PHP est adapté au développement web côté serveur.
Il fonctionne bien avec Apache.
Il permet de créer rapidement une API REST.
Il permet de montrer clairement les notions de contrôleur, modèle, repository, session, sécurité et accès base de données.

Le projet n'utilise pas de framework PHP lourd afin de rendre visibles les mécanismes internes :
- routage ;
- lecture des requêtes JSON ;
- création des réponses JSON ;
- sessions ;
- rôles ;
- accès SQL avec PDO.

Pourquoi MariaDB ?

MariaDB est une base relationnelle adaptée au projet, car les données sont fortement liées.

Exemples de relations :
- une commande peut contenir plusieurs produits ;
- une commande peut contenir plusieurs menus ;
- un menu est composé de produits ;
- un produit dépend d'ingrédients ;
- un utilisateur possède un rôle ;
- une commande possède un statut ;
- une commande provient d'un canal.

Pourquoi Docker ?

Docker permet d'isoler les services.
Le projet peut tourner avec les mêmes versions de PHP, Apache et MariaDB.
Docker évite les problèmes d'environnement entre le développement et le serveur.

Pourquoi séparer front et back ?

La borne client est séparée du backend.
Elle consomme l'API via des requêtes HTTP.

Avantages :
- séparation claire des responsabilités ;
- le front ne contient pas le code PHP ;
- le backend reste responsable des prix, du stock et de la sécurité ;
- le front peut évoluer vers un framework sans réécrire tout le backend.

6. ARCHITECTURE MVC

Le projet suit une architecture proche du MVC.

MVC signifie :
- Model : représente les données métier.
- View : affiche l'interface.
- Controller : reçoit les requêtes et coordonne les traitements.

Dans WACDO :

- Les Models sont dans app/Models.
- Les Views sont dans app/Views et index.html.
- Les Controllers sont dans app/Controllers.
- Les accès SQL sont séparés dans app/Repositories.

Exemple :

CommandeController reçoit une demande de création de commande.
Il valide les données.
Il appelle DbCommandeRepository.
DbCommandeRepository insère la commande en base.
La réponse est renvoyée en JSON.


7. ROLE DES REPOSITORIES

Les repositories sont des classes responsables de l'accès à la base de données.

Ils évitent de mettre les requêtes SQL directement dans les contrôleurs.

Repositories principaux :

- DbCommandeRepository.php
- DbProduitRepository.php
- DbMenuRepository.php
- DbIngredientRepository.php
- DbUtilisateurRepository.php
- DbCategorieRepository.php

Avantages :
- code plus organisé ;
- responsabilités séparées ;
- contrôleurs plus lisibles ;
- SQL centralisé.

16. PARCOURS D'UNE COMMANDE

Étapes côté client :

1. Le client ouvre la borne.
2. Le client choisit sur place ou à emporter.
3. Le client consulte le catalogue.
4. Le client ajoute des produits ou menus au panier.
5. Le client valide la commande.

Étapes côté backend :

1. L'API reçoit le JSON de commande.
2. Le contrôleur vérifie les données.
3. Le repository ouvre une transaction.
4. Le backend vérifie produits et menus.
5. Le backend vérifie les disponibilités.
6. Le backend calcule les prix.
7. Le backend insère la commande.
8. Le backend insère les lignes.
9. Le backend calcule les ingrédients nécessaires.
10. Le backend débite le stock.
11. Le backend met à jour le total.
12. Le backend valide la transaction.

Point important :
Le front ne calcule pas le prix final de confiance.
Le serveur recalcule le prix final.


17. STATUTS DE COMMANDE

Statuts disponibles :
- en_attente
- en_preparation
- prete
- servie
- annulee

Transitions autorisées :

en_attente vers en_preparation
en_attente vers annulee
en_preparation vers prete
en_preparation vers annulee
prete vers servie
prete vers annulee
servie vers fin
annulee vers fin

Justification :
Une commande ne doit pas changer d'état n'importe comment.
Le workflow évite les incohérences métier.


18. GESTION DU STOCK

Le stock est géré côté backend.

Lorsqu'une commande est créée :
- le backend calcule les ingrédients nécessaires ;
- le backend vérifie le stock ;
- le backend débite les ingrédients.

Lorsqu'une commande est annulée :
- le backend recrédite les ingrédients.

Avantage :
Le stock ne dépend pas du front, qui pourrait être modifié par l'utilisateur.
